## 第1章 問4の解き方（最初に読む）

### 1-1. 問4はどういう問題か

ある会社のシステム（Webサービス、IoT、動画配信、基幹システムの移行など）の**構成を決める・見直す**場面が題材。設問は次の3種類。

1. **計算**：処理時間、データ量、転送時間、稼働率、必要台数、料金
2. **構成の選択とその理由**：どのクラウドサービスを使うか、処理をどこに置くか
3. **問題点と対策**：性能が出ない理由、障害時に何が起きるか、改善の理由

### 1-2. 解く手順

1. **表の数値と注記に印を付ける**：「1件当たり」「1日当たり」「ピーク時」「実効速度は〜%」「〜は無視する」。
2. **計算の前に単位をそろえる**（2-1）。バイトとビット、ミリ秒と秒、MとG。
3. **「何を足して、何を足さないか」を書き出してから計算する**：処理の流れ図を見て、該当する処理だけを足す。
4. **端数処理の指示**（切上げ・切捨て・四捨五入、小数第何位まで）を答えの直前に確認する。
5. 記述は「**何が・なぜ・どうなるか**」を本文の機器名で書く。

### 1-3. 採点講評が毎年言っていること

| 失点の原因 | 講評での言われ方（例） | 防ぎ方 |
|---|---|---|
| 計算対象の漏れ | PCに格納されているデータを考慮していない（2021秋） | 計算前に足すものを列挙 |
| 問われた量と違うもの | 送信データ量を問うのに通信速度や回数を答えた（2021春） | 設問の名詞（量・時間・回数）を確認 |
| 境界値の誤り | 制約を回避する実行間隔の値の誤り（2022春） | 「以上・超える・未満」を問題文どおりに |
| サービス形態の混同 | SaaSをPaaSやIaaSと混同（2023秋） | 2-6の表を覚える |
| 抽象的な答え | メモリ、ネットワークなどの用語だけを挙げた（2020） | 「どの機器の何が」まで書く |
| 理由が浅い | レスポンスが改善した理由を踏み込んで考えていない（2024春） | データ量・往復回数・処理場所のどれが変わったかを書く |
| 業務を見ない | データ量や速度だけに着目し、業務内容を見ない（2024秋） | 「誰がどの業務で使うか」を考える |

## 第2章 必ず知っておく基礎知識

### 2-1. 単位と換算

| 換算 | 値 |
|---|---|
| 1バイト | 8ビット（★回線速度はビット/秒、データ量はバイトで書かれることが多い） |
| k・M・G・T | 10³・10⁶・10⁹・10¹²（問題文で2¹⁰系と指定されたらそれに従う） |
| 1ミリ秒 | 10⁻³秒 |
| 1日 | 86,400秒 |
| 1年 | 8,760時間（365日） |

### 2-2. 性能（応答時間・スループット・ボトルネック）

| 用語 | 意味 |
|---|---|
| **応答時間（レスポンスタイム）** | 要求してから応答が返るまでの時間 |
| **スループット** | 単位時間に処理できる件数 |
| **ボトルネック** | 全体の性能を決めている最も遅い部分。そこを改善しないと全体は速くならない |
| **CPU使用率** | 処理時間の合計 ÷ 経過時間 |

**応答時間の積上げ**
- **順番に**処理する部分は**足し算**。
- **同時に（並列に）**処理する部分は**最も遅いものの時間**（最大値）。
- 例：前処理10ミリ秒＋（A 30、B 40、C 200 を同時に呼ぶ）＝ 10 ＋ 200 ＝ 210ミリ秒。順番に呼ぶと 10＋30＋40＋200 ＝ 280ミリ秒。

**待ち行列（M/M/1）**：利用率 ρ ＝ 到着率 × 平均処理時間。平均待ち時間 ＝ ρ ÷ (1 − ρ) × 平均処理時間。**利用率が1に近づくと待ち時間が急に増える**。

### 2-3. データ量と転送時間

| 計算 | 式 |
|---|---|
| 転送時間 | データ量[ビット] ÷ (回線速度[ビット/秒] × 伝送効率) |
| 非圧縮の動画のデータ量 | 横の画素数 × 縦の画素数 × 1画素のビット数（bpp）× 1秒のフレーム数（fps）× 秒数 |
| 必要な帯域 | 1件のデータ量 × 1秒当たりの件数 |
| 保存容量 | 1日のデータ量 × 保存日数（× 余裕率） |

**例**：1.2Tバイトを1Gビット/秒・実効60%で送る → 1.2 × 10¹² × 8 ÷ (10⁹ × 0.6) ＝ 16,000秒 ≒ 4.4時間。

**データ量を減らす工夫**（2025秋）：解像度・フレーム数を下げる、白黒にする、必要な範囲だけ切り出す、エッジで解析して結果だけを送る、圧縮する。

### 2-4. 可用性（稼働率・冗長化）

| 計算 | 式 |
|---|---|
| 稼働率 | MTBF ÷ (MTBF ＋ MTTR)　（MTBF：平均故障間隔、MTTR：平均修理時間） |
| **直列**（全部動かないとだめ） | A × B |
| **並列**（どれか1つ動けばよい） | 1 − (1 − A)(1 − B) |
| 年間停止時間の上限 | (1 − 稼働率) × 8,760時間　（99.9% → 8.76時間、99.99% → 約53分） |

- 直列に構成要素が増えると稼働率は下がる（マイクロサービスで呼び出すサービスが増える場合など）。
- **単一障害点（SPOF）**：そこが止まると全体が止まる部分。冗長化して取り除く。
- 冗長化の方式：**ホットスタンバイ**（待機系が常に起動、すぐ切替え）、ウォームスタンバイ、**コールドスタンバイ**（故障してから起動）。**アクティブ・アクティブ**（両方で処理）と**アクティブ・スタンバイ**。
- **フェールオーバ**：故障時に待機系へ自動で切り替えること。

### 2-5. 台数の計算とスケーリング

| 計算 | 式 |
|---|---|
| 同時処理数 | 到着率（件/秒）× 1件の処理時間（秒） |
| 必要台数 | 必要な処理能力 ÷ 1台の処理能力（**切り上げ**） |
| 余裕率を持たせる | 1台の処理能力 × 目標使用率（例：70%以下）で割る |
| 1台故障しても処理できる | 必要台数 ＋ 1（N＋1冗長） |

- **スケールアウト**：台数を増やす。**スケールアップ**：1台の性能を上げる。
- **オートスケール**：負荷に応じて台数を自動で増減する（クラウド）。

### 2-6. クラウドサービスの形態と責任範囲

| 形態 | 事業者が管理 | 利用者が管理 | 向いている場面 |
|---|---|---|---|
| **IaaS** | ハードウェア、仮想化基盤 | **OS**、ミドルウェア、アプリ、データ | OSの設定を変えたい、既存の環境をそのまま移したい |
| **PaaS** | ＋OS、ミドルウェア | アプリ、データ | 運用負荷（パッチ、バックアップ）を減らしたい。**負荷に応じた自動の増減** |
| **SaaS** | ＋アプリ | 設定、データ | 標準の機能で足りる。カスタマイズや他システムとの連携に**制約** |
| **FaaS（サーバレス）** | ＋実行環境全体 | 関数のコード | 処理の時だけ動かして課金。**実行時間の上限、起動の遅れ（コールドスタート）、同時実行数の上限**がある（2022春） |

- **責任共有モデル**：どこまでを事業者が責任を持ち、どこからを利用者が持つか。IaaSでは**OSのパッチ適用は利用者の仕事**。
- **SLA**：稼働率などの約束。下回ったときは**利用料の一部を減額**するのが一般的で、**業務停止による損失までは補償されない**（2025春）。
- **提供形態**：パブリック（共用）／プライベート（専用）／ハイブリッド（組合せ）。

### 2-7. 仮想化とコンテナ

| 方式 | 仕組み | 特徴 |
|---|---|---|
| **ハイパーバイザー型** | ハードウェアの上に直接、仮想化ソフト | 性能の低下が小さい。サーバ統合の主流 |
| **ホスト型** | 普通のOS（ホストOS）の上で仮想化ソフトを動かす | 手軽。性能の低下が大きい |
| **コンテナ型** | ホストOSのカーネルを共有し、アプリの実行環境だけを分ける | **起動が速く軽い**。ホストOSと違う種類のOSは動かせない（2022秋） |

- **リソースの予約（下限値）・上限値・優先度**：仮想サーバに最低限のCPU・メモリを確保する（2017春）。
- **ライブマイグレーション**：動いたまま別の物理サーバに移す。

### 2-8. Webシステムの方式

| 方式・用語 | 一言で |
|---|---|
| **Web API**（REST） | URLとHTTPのメソッドで処理を呼び出し、**JSON**でデータを返す |
| **SPA**（シングルページアプリケーション） | 最初に画面の部品（JavaScript）を受け取り、以降はAPIでデータだけを取得して画面の一部を書き換える。転送量と待ち時間が減る（2023春） |
| **BFF**（フロントエンド専用のサーバ） | 画面ごとに必要なAPIの呼出しをまとめて1回で返す。**往復回数と端末側の処理が減る**（2024春） |
| **負荷分散装置（ロードバランサ）** | 複数のサーバに要求を振り分ける。**ヘルスチェック**で故障したサーバを外す。セッションを同じサーバに送り続ける設定（セッション維持）が必要な場合がある |
| **リバースプロキシ** | サーバの手前で要求を受け、キャッシュやTLSの終端を行う |
| **CDN** | 静的なファイルを利用者の近くのサーバから配信する |

### 2-9. キャッシュ

**一言で**：時間がかかる処理の結果を手前に保存しておき、次から速く返す仕組み。

- 置き場所：ブラウザ、CDN、リバースプロキシ、アプリケーションのメモリ、専用のキャッシュサーバ。
- **キャッシュヒット率**が高いほど効果が大きい。
- 論点：**いつ更新するか**（元のデータが変わったのに古いままだと誤った情報を返す）。2023春：負荷が高いときにキャッシュの更新処理が動かないと、古い記事が表示され続ける。

### 2-10. IoT・エッジコンピューティング

| 用語 | 一言で |
|---|---|
| **LPWA** | 低消費電力で広い範囲を通信できるが、**通信速度が遅く送れるデータ量が少ない**（LTE-M、NB-IoTなど） |
| **MQTT** | IoT向けの軽い通信方式。**ブローカ**を介した**出版／購読（Pub/Sub）型**。送信側と受信側が直接つながらない |
| **エッジコンピューティング** | データの発生場所の近く（現場の小型コンピュータ）で処理する。**通信量の削減、応答の速さ、通信が切れても動く** |
| **GPU** | 同じ計算を大量に並列で行う。動画処理・AIの推論に向く（2024秋） |

**処理をどこに置くか**の判断軸：データ量（送れるか）、応答時間（間に合うか）、機器の性能（処理できるか）、通信が切れた時（止まってよいか）。

### 2-11. マイクロサービス

**一言で**：システムを機能ごとの小さなサービスに分け、独立して開発・リリースできるようにする構成（シラバスの用語例）。

| 利点 | 注意点 |
|---|---|
| 一部だけ改修・リリースできる | サービス間の呼出しで遅くなる |
| 負荷の高いサービスだけ増やせる | 直列に依存するサービスが増えると**稼働率が下がる** |
| 障害の影響を局所化できる（設計次第） | 1つの遅延が呼出し元の資源（スレッド）を使い果たし、**障害が連鎖**する |
| | サービスをまたいだ**トランザクションが使えない** → 失敗時に**取消し処理（補償）**が必要 |

- **サーキットブレーカー**（用語例）：失敗が続くサービスへの呼出しを一定時間止め、すぐに失敗として扱う。障害の連鎖を防ぐ。
- **タイムアウト**：応答の待ち時間に上限を設ける。

### 2-12. 災害対策（BCP・DR）

| 用語 | 意味 |
|---|---|
| **RPO**（目標復旧時点） | どの時点のデータまで戻せればよいか（例：1時間前まで） |
| **RTO**（目標復旧時間） | 何時間以内に復旧するか |
| バックアップ方式 | フル（全部）、差分（前回のフルからの変更）、増分（前回のバックアップからの変更） |
| ホットサイト／ウォームサイト／コールドサイト | 待機設備の準備度合い |
| マルチリージョン | 離れた地域のデータセンタに分散 |

### 2-13. 非機能要件

機能（何ができるか）以外の要件。**可用性・性能・拡張性・運用保守性・移行性・セキュリティ**（IPAの非機能要求グレードの分類）。問題文の要件表で「稼働率」「応答時間」「同時利用者数」「データ保存期間」が示され、構成がそれを満たすかを計算で確認させる。

### 2-14. 生成AIを組み込んだシステム（今後の題材候補）

- **RAG**：社内文書を検索し、その内容をLLMに渡して回答させる構成（用語例にない語だが、LLM・プロンプトエンジニアリングは用語例）。
- 性能：LLMの応答は出力の長さに比例して時間がかかる → **生成された文字から順に表示する**と表示開始が早くなる。
- 料金：**入力と出力のトークン数**に比例する従量課金。キャッシュで呼出し回数を減らす。
- 外部APIの制約：**1分当たりの呼出し回数の上限**、応答しないときの**タイムアウト**。

## 第3章 よく出る問題の型（5パターン）

### 型1：クラウドへの移行（2025春、2023秋、2022春、2021秋、2018春）
- 問われること：サービス形態の選択とその理由、SLA（稼働率と減額）、移行時間の計算、料金の見積り、責任範囲。

### 型2：Webシステムの性能改善（2024春、2023春、2019春、2014春）
- 問われること：応答時間の内訳、SPA／BFF／キャッシュで何が減るか、APIの呼出し回数、負荷の高い機器と追加する機器。

### 型3：IoT・エッジ・動画（2025秋、2024秋、2021春、2020、2019秋）
- 問われること：データ量と帯域の計算、処理の置き場所、LPWA・MQTTの特徴、ストレージ容量。

### 型4：仮想化・コンテナ・並列処理（2022秋、2018秋、2017春、2015春）
- 問われること：方式の特徴、リソースの割当て、ボトルネック、並列化の効果が出る処理と出ない処理。

### 型5：可用性・災害対策（2025春、2016秋）
- 問われること：稼働率の計算、冗長化、RPO／RTO、切替え手順。

## 第4章 計算・記述の書き方（良い答え・悪い答え）

### 4-1. 計算

**例**：「逐次表示方式で表示が始まるまでの時間」（処理：前処理0.1秒、検索0.3秒、生成開始まで0.5秒、残りの生成8.0秒、後処理0.1秒）

| | 答え | 評価 |
|---|---|---|
| ✕ | 9.0秒 | 全部足している。表示開始は先頭の文字を受け取った時点 |
| ✕ | 1.0秒 | 後処理（全文受信後）まで足している |
| ○ | 0.1 ＋ 0.3 ＋ 0.5 ＝ 0.9秒 | 表示開始までの処理だけを足している |

### 4-2. 記述

**例1**：「BFFを置いてレスポンスが改善した理由」

| | 答え | 評価 |
|---|---|---|
| ✕ | サーバが増えたから | 原因を説明していない |
| ○ | 画面に必要なデータをBFFが1回の応答にまとめるので，端末とサーバ間の往復回数が減ったから | 何が減ったかを書いている |

**例2**：「SLAの減額規定だけでは不十分な理由」

| | 答え | 評価 |
|---|---|---|
| ✕ | 稼働率が低いから | 問いとずれている |
| ○ | 減額は利用料の一部に限られ，業務停止による自社の損失は補償されないから | |

**記述の型**

| 問われ方 | 型 |
|---|---|
| 改善した理由 | 「〜を〜で行うことで，〜（転送量・往復回数・処理時間）が減ったから」 |
| 構成の問題点 | 「〜が単一障害点となり，〜が停止すると〜できなくなる」 |
| 採用した理由 | 「〜の要件を満たし，かつ〜の制約を回避できるから」 |
| 障害が広がる理由 | 「〜の応答待ちが〜の資源を占有し，他の処理ができなくなるから」 |

## 第5章 2026年度に向けて

### 5-1. 直近の出題

| 年度 | 春期 | 秋期 |
|---|---|---|
| 2025 | BEMSのクラウド移行（SLA） | エッジの動画配信（ハードウェアとネットワークの制約） |
| 2024 | CRMの改修（BFF） | 動画配信（CPUとGPU、機能の配置） |
| 2023 | ニュース配信（SPA、キャッシュ） | 合併時のシステム統合（SaaS） |
| 2022 | 名刺管理（PaaS、FaaS、料金） | 開発環境（コンテナ） |

**傾向**：2024年度以降は**ハードウェアや通信の制約を考えた配置**（GPU、エッジ、帯域）が増えている。クラウドはほぼ毎年どこかに出る。
