## 第1章 問10の解き方（最初に読む）

### 1-1. 問10はどういう問題か

ある会社の情報システム部門が、社内外にITサービス（業務システム、サービスデスクなど）を提供している場面が題材。〔サービスの概要〕〔SLA〕〔運用の手順〕などの段落と、SLAの表・手順の表・グラフが付く。設問は次の3種類。

1. **用語・プロセスの空欄**（どのプロセスの活動か、エスカレーションの種類など）
2. **計算**（サービス提供時間、稼働率、停止可能時間、要員の工数、費用の配賦）
3. **運用上の対応**（誰と何を合意するか、手順に何を加えるか、改善策）

### 1-2. 解く手順

1. **SLAの表と注記を最初に読む**：サービス時間（何時から何時、休日は）、計画停止をどう扱うか、目標値。
2. **登場する組織（顧客、サービス提供者、外部の供給者、社内の他部門）と、その間の合意を図にする**。
3. **本文で「既に決まっていて変えられないこと」に印を付ける**（例：「件数は1か月前に提示することになっている」）。
4. **設問の「〜管理の観点から」「〜の視点で」に印を付ける**：答えの範囲が限定される。
5. 記述は**本文の手順・ルールに沿った**具体的な対応を書く（一般論は点にならない）。

### 1-3. 採点講評が毎年言っていること

| 失点の原因 | 講評での言われ方（例） | 防ぎ方 |
|---|---|---|
| SLAを安易に変えようとする | “合意しているSLAの変更を協議する”という解答（2025春） | まず業務に支障を出さない施策を考える |
| プロセスの混同 | 回避策と根本原因（2022春）、標準変更と通常変更（2024秋）、展開管理の意味（2024春） | 2-4〜2-8 |
| エスカレーションの混同 | 階層的と機能的の違い（2018春） | 2-3 |
| 成果と手段の混同 | パッケージ導入を成果とした（2022秋） | 成果は測定できる指標で書く |
| 本文の制約を無視 | 体制を増強できないことを読み取れない（2023秋） | 決まっていることに印 |
| 主体の取り違え | サービスデスク以外の部門の作業を書いた（2021春、2017秋） | 設問の主語を確認 |
| 計算の条件漏れ | 件数の増加や集中を考えない（2024秋）、システム処理時間を加算（2022秋） | 計算に使う要素を書き出す |
| 目的と理由の取り違え | 目的を問うのに理由を書いた（2018秋） | 目的は「〜するため」 |

## 第2章 必ず知っておく基礎知識

### 2-1. サービスマネジメントとは

**一言で**：ITサービスを、顧客と合意した品質で、安定して提供し続けるための管理の仕組み。規格は **JIS Q 20000**、実践の手引きとして **ITIL** がある。

| 用語 | 意味 |
|---|---|
| **サービス** | 顧客が望む成果を、顧客がコストやリスクを負わずに得られるようにする手段 |
| **顧客** | サービスを受ける組織（費用を払い、SLAに合意する） |
| **利用者** | 実際にサービスを使う人 |
| **サービス提供者** | サービスを提供する組織（情報システム部門など） |
| **供給者** | サービス提供者を支える外部の会社（クラウド事業者、委託先）。社内の他部門は**内部供給者** |
| **サービスカタログ** | 提供しているサービスの一覧と内容（2023春） |

### 2-2. サービスレベル管理とSLA

**一言で**：顧客と**サービスの品質の目標（サービスレベル）**を合意し（**SLA**）、実績を測って報告し、達成できないときは改善する。

**SLAに書く項目の例**：サービス時間、稼働率、応答時間、障害時の回復時間、サービスデスクの受付時間、問合せへの回答時間。

**稼働率の計算**（SLAの定義に従う）

> サービス提供時間 ＝ サービス時間の合計 − **計画停止時間**（SLAで除外すると定めている場合）
> 稼働率 ＝ (サービス提供時間 − 停止時間) ÷ サービス提供時間
> 停止できる時間 ＝ サービス提供時間 × (1 − 目標稼働率)

**例**：平日20日、9時〜21時（12時間）、月1回の計画停止2時間は除く → サービス提供時間 ＝ 20 × 12 − 2 ＝ 238時間。目標99.5%なら停止できる時間は 238 × 0.005 ＝ 1.19時間。

**ポイント**
- **SLAと、供給者との合意の整合**：顧客との目標を守るには、供給者（クラウド事業者、内部の他部門）とも、それに見合う目標を合意しておく必要がある（2023秋、2019春）。
- 供給者の**保守時間**も計画停止として考える必要がある（2019春）。
- SLAは、インシデントが起きたからといって簡単に変えるものではない（2025春）。

### 2-3. サービスデスク

**一言で**：利用者からの問合せ・依頼・障害の連絡を受け付ける**単一の窓口（SPOC）**。

| 用語 | 意味 |
|---|---|
| **SPOC**（単一窓口） | 問合せ先を1つにまとめる。利用者が迷わず、記録も一元化できる（2025秋） |
| **一次解決** | サービスデスクだけで解決すること |
| **FAQ・ナレッジ** | よくある問合せと答え。利用者の**自己解決**を増やし、問合せを減らす（2017秋：FAQを更新した翌日に電話が減った） |
| **機能的エスカレーション** | 専門知識を持つ**別のチーム**（2次サポート、開発課）に引き継ぐ |
| **階層的エスカレーション** | 対応の判断のため、**上位の管理者**に報告する（2018春で混同が多かった） |

**要員の計算**（2024秋）

> 必要な工数 ＝ 問合せ件数 × 1件の平均対応時間
> 必要な人数 ＝ 必要な工数 ÷ 1人の対応可能時間
> ★**件数の増加見込み**や、**特定の時間帯への集中**を考えて余裕を持たせる

### 2-4. インシデント管理

**一言で**：サービスの中断や品質の低下（インシデント）から、**できるだけ早くサービスを元に戻す**こと。

**流れ**：記録 → 分類・優先度付け（影響度 × 緊急度）→ 調査・診断 → （必要ならエスカレーション）→ 解決・復旧 → 終了

- 根本原因が分からなくても、**回避策**（ワークアラウンド）で業務を再開させればよい。
- 同じインシデントの傾向を分析して、問題管理に回す。

### 2-5. 問題管理

**一言で**：インシデントの**根本原因**を突き止め、**再発を防ぐ**こと。

| 用語 | 意味 |
|---|---|
| **問題** | 1つ以上のインシデントの原因（まだ分かっていないものを含む） |
| **既知の誤り** | 根本原因や回避策が分かっている問題。記録しておくと、次に同じインシデントが起きたとき早く回避策を適用できる（2022春） |
| **傾向分析（トレンド分析）** | インシデントの記録を分析し、繰り返し起きているものを見つける（2017春） |
| **恒久対策** | 根本原因を取り除く。システムの変更が必要なら**変更要求（RFC）**を出す |

**インシデント管理との違い（★）**：インシデント管理は「早く直す」、問題管理は「二度と起きないようにする」。回避策があっても、根本原因が取り除かれていなければ再発は止まらない（2022春で正答率が低かった）。

### 2-6. サービス要求管理

**一言で**：障害ではない、定型的な依頼（パスワードのリセット、アカウントの発行、ソフトウェアのインストール）を処理すること。手順が決まっているので、サービスデスクで完結させやすい。

### 2-7. 変更管理

**一言で**：サービスやシステムへの変更を、**リスクを評価して承認してから**行うこと。

**流れ**：変更要求（RFC）→ 記録 → 影響とリスクの評価 → **承認**（変更諮問委員会など）→ 計画 → 実施（展開）→ レビュー

| 変更の種類 | 意味 |
|---|---|
| **標準変更** | リスクが低く手順が決まっていて、**事前に承認済み**の変更（毎回の承認が不要。サービスデスクに任せられる。2024秋） |
| **通常変更** | 毎回、評価と承認が必要な変更 |
| **緊急変更** | 重大な障害の対応など、急いで行う変更（承認の手続を簡略化） |

- 承認者の負担を減らすため、優先度の低い変更の承認を下位に**権限委譲**することがある（2021秋）。
- 変更の**成果**は、**測定できる指標**で定義する（例：「売掛金の回収率を〜%に上げる」。2022秋）。

### 2-8. リリース及び展開管理

**一言で**：承認された変更を、**本番環境に確実に展開する**こと。

- **展開計画**：いつ、どの手順で、誰が行うか。サービスの停止時間内に終わるか。
- **切戻し計画**：展開に失敗したり、展開中にインシデントが起きたりしたときに、**元に戻す手順**（2021秋、2016秋）。
- **展開前のテスト**：例えばOSのパッチを利用者のPCに配る前に、情報システム部で業務アプリが正常に動くかを確かめる（2017春、2024春）。
- サービスデスクへの**引継ぎ**：新しいサービスや変更の内容を、サービスデスクが対応できるよう事前に伝える（2024春、2021春）。

### 2-9. 構成管理

**一言で**：サービスを構成する要素（**構成品目、CI**：サーバ、ソフトウェア、ネットワーク機器、文書）とその関係を、正確に記録しておくこと。記録の場所を**CMDB**（構成管理データベース）という。変更管理・インシデント管理の判断の基礎になる。

### 2-10. 容量・能力（キャパシティ）管理

**一言で**：今と将来の需要に対して、**必要な資源（CPU、メモリ、ストレージ、ネットワーク、人）を過不足なく確保**すること。

**活動**
1. **監視**：CPU使用率、ストレージ使用率、応答時間、処理件数を測る。平均だけでなく**ピーク**を見る（2015秋）。
2. **分析・予測**：業務量の増加（事業計画、営業部門の見込み）から将来の需要を予測する。**需要の情報を事業部門から定期的に入手する**（2018秋）。
3. **キャパシティ計画**：いつ、何を増強するかを計画する。予測から外れたら見直す（2016春）。
4. **需要管理**：資源を増やすのではなく、**運用方法を変えて**負荷を減らす・分散する（処理の時間帯をずらす、優先度を付ける。2016春）。

**クラウドの場合**（2025春）：資源を柔軟に追加・削除できるが、使用量と費用を監視し、適切に割り当てる必要がある。

### 2-11. サービス可用性管理とサービス継続管理

| 管理 | 目的 | 内容 |
|---|---|---|
| **サービス可用性管理** | 合意した可用性（稼働率）を満たす | 冗長化、障害の監視、**MTBF**（平均故障間隔）・**MTRS**（平均サービス回復時間）の改善、計画停止の調整（2023春） |
| **サービス継続管理** | 災害などの重大な事態でもサービスを続ける | 継続計画、バックアップの遠隔地保管、訓練（2023春：待機系への切替えだけでは、広域災害時のマルウェアからのデータ保護として不十分） |

> 稼働率 ＝ MTBF ÷ (MTBF ＋ MTRS)

**ファシリティ**（2018春）：電源、空調、建物。重要な機器への電力は**二重化**する。

### 2-12. 供給者管理

**一言で**：外部の供給者（クラウド事業者、運用の委託先）や内部供給者が、サービスの目標に沿って役割を果たすよう、**契約・合意し、実績を監視する**こと。

- 顧客とのSLAを守るために、供給者との合意（契約上のサービスレベル）を**SLAと整合させる**。
- クラウドでは、**事業者と自社の責任範囲**を理解する。例：PaaSの障害が復旧しても、自社のアプリの確認が終わるまでサービスは再開できない（2016秋）。

### 2-13. サービスの予算業務及び会計業務

**一言で**：サービスにかかる費用を把握し、部門などに**配分（配賦）**すること（2020）。

| 用語 | 意味 |
|---|---|
| **直接費** | 特定のサービス（部門）だけのために使う費用 → そのまま割り当てる |
| **間接費** | 複数のサービスで共通に使う費用 → 基準（利用者数、利用時間、件数）で按分する（**配賦**） |

**例**：共通基盤の費用 1,000万円を、利用時間の比 A：B ＝ 3：2 で配賦 → A に 600万円、B に 400万円。
- 共有するようになった資源は、直接費から間接費に変えて配賦するのがふさわしい（2020）。

### 2-14. KPI・CSFと継続的改善

| 用語 | 意味 | 例 |
|---|---|---|
| **CSF**（重要成功要因） | 目標を達成するために特に重要なこと | インシデントを迅速に解決する |
| **KPI**（重要業績評価指標） | CSFの達成度を測る指標 | 一次解決率、平均解決時間、自己解決率 |

- 改善は、KPIと目標値を決め、実績を測り、評価して手を打つ（PDCA）。改善活動を組織に定着させるには、**運用部門のトップが方針と評価基準を示す**（2019秋）。

### 2-15. 運用の新しい考え方

| 用語 | 意味 |
|---|---|
| **SRE** | ソフトウェア開発の手法で運用を自動化・改善する考え方（用語例） |
| **エラーバジェット** | 目標の稼働率から許される停止時間の「予算」。予算が残っている間は変更を進め、使い切ったら安定化を優先する（用語例にはない） |
| **AIOps** | AIで監視データを分析し、障害の予兆検知や原因の特定を支援する（用語例） |
| **チャットボット** | サービスデスクの一次対応を自動化（用語例「AIの活用（チャットボットなど）」） |

## 第3章 よく出る問題の型（5パターン）

### 型1：サービスデスクの改善・立上げ（2025秋、2024秋、2024春、2017秋、2017春）
- 問われること：SPOC、FAQと自己解決率、エスカレーション、要員の工数、引継ぎ。

### 型2：キャパシティ管理（2025春、2018秋、2016春、2015秋）
- 問われること：監視項目、需要の予測と情報の入手、増強時期の見直し、需要管理、インシデント時の業務への配慮。

### 型3：SLAと供給者（2023秋、2023春、2021春、2019春、2016秋）
- 問われること：サービス提供時間と稼働率の計算、計画停止、供給者との合意、責任範囲。

### 型4：インシデント・問題・変更（2022秋、2022春、2021秋）
- 問われること：プロセスの区別、既知の誤りと回避策、変更の種類、権限委譲、切戻し計画、作業工数。

### 型5：費用・改善（2020、2019秋）
- 問われること：直接費と間接費、配賦の基準、KPIと目標値、改善の体制。

## 第4章 記述の書き方（良い答え・悪い答え）

**例1**：「インシデントの発生で翌日の製造業務に支障が出ないよう、営業部と製造部で協議すべきこと」（2025春型）

| | 答え | 評価 |
|---|---|---|
| ✕ | SLAの目標値を緩和する | SLAはインシデントを理由に変えない |
| ○ | 受注データの締め時刻を早め，翌日の製造に必要な処理を先に終えること | 業務に支障を出さない具体策 |

**例2**：「再発インシデントを減らすために抽出すべき問題の条件」（2022春型）

| | 答え | 評価 |
|---|---|---|
| ✕ | 回避策が策定されている問題 | 回避策があっても根本原因が残れば再発する |
| ○ | 根本原因と解決策が特定されていない問題 | |

**例3**：「変更を実施して得られる成果」（2022秋型）

| | 答え | 評価 |
|---|---|---|
| ✕ | 新しいパッケージを導入すること | 手段 |
| ○ | 売掛金の回収率を〜%に向上させること | 測定できる成果 |

**記述の型**

| 問われ方 | 型 |
|---|---|
| 目的 | 「〜することで，〜（SLA・KPIの目標）を達成するため」 |
| 必要な作業 | 「〈いつ〉の前に，〈誰〉が〈何〉を確認（テスト）する」 |
| 合意すべき事項 | 「〈相手〉と〈項目：計画停止時間・サービス時間・件数〉について合意する」 |
| 改善策 | 「〜を〜に変更し，〜（件数・時間）を減らす」 |
| KPI | 「〜率」「〜件数」「〜時間」（測れる指標の名前） |
